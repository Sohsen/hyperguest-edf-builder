Basic structure of the Hotel EDF﻿

Last modified: 25 February 2026

In this section, the basic structure and essential elements of the Hotel EDF are explained in detail.

note

This overview explains only the essential parts that are required for most or all Hotel EDF files. For comprehensive and detailed information on all elements and attributes within the Hotel EDF, consult the schema files.

Each Hotel EDF file represents a single hotel contract. This means that each hotel's information is represented in its own EDF file (or multiple EDF files, if there are multiple contracts for one hotel). The root element of any Hotel EDF file is <HotelRoot>. The root element must contain the XML namespace of the schema, as well as the version that was used for creating the EDF (<HotelRoot>/@SchemaVersion).

Within <HotelRoot>, each EDF file is divided into two sections: <BasicData> and <SellingData>.

BasicData attributes﻿

The <BasicData> element contains all relevant metadata about the hotel itself and the corresponding hotel contract. Important attributes of the <BasicData> element include:

Code﻿

Required by the XSD

The @Code attribute specifies the unique ID assigned to the hotel. The ID is defined by the supplier / EDF provider. The Code is transferred throughout the entire search and booking process. Therefore, it needs to match the Code defined within the Content EDF and Allotment EDF (and the B-Hub). It is used as one of the Hotel identifiers.

The attribute is mapped to the following positions in the Hub / B-Hub requests:

  • Hub: /HotelOfferResponse/Hotel/Offers/Offer[1]/@ProductCode

  • B-Hub: /CheckRequest/Offers/Offer/HotelOnly/Hotels/Hotel/BookingCode

It needs to match the value defined within:

  • Content EDF: BasicData/@Code (required in Content Player)

  • Allotment EDF: BasicData/@Code (required by XSD)

TourOperatorCode﻿

Required by the XSD

The @TourOperatorCode attribute represents the supplier / EDF provider with a unique ID (set up by Peakwork).

The attribute is mapped to the following positions in the Hub / B-Hub requests:

  • Hub: /HotelOfferResponse/Hotel/Offers/Offer[1]/TourOperator/@Code

  • B-Hub: /CheckRequest/Offers/Offer/HotelOnly/Touroperator/Code

It needs to match the value defined within:

  • Content EDF: BasicData/@TourOperatorCode (required in Content Player)

  • Allotment EDF: BasicData/@TourOperatorCode (required by XSD)

Usage﻿

Required by the XSD

This attribute specifies the usage context of the hotel contract. Possible values are HotelOnly, Package or Dynamic. Note that HotelOnly means that the prices defined in the EDF are pure hotel prices (not including flights, extras like transfers etc.). For example, as a bedbank, all your EDF files should include the Usage HotelOnly. The @Usage attribute is not related to distribution channels etc.!

The following request type is used in the Hub / B-Hub according to the value:

  • Hub: /PackageOfferResponse/Hotel/Offers/Offer or /HotelOfferResponse/Hotel/Offers/Offer

  • B-Hub: /CheckRequest/Offers/Offer/HotelOnly or /CheckRequest/Offers/Offer/Package

It needs to match the value defined within:

  • Content EDF: not used

  • Allotment EDF: BasicData/@Usage

FileKey﻿

The @FileKey specifies a unique ID for the individual hotel contract in order to create unique file names. It is used to differentiate multiple contracts / EDF files that belong to the same hotel during the pre-process and also as an identifier for season merge.

Consider that the FileKey attribute is not used in the PXB processing and thus not in the Player or Hub. As an individual hotel identifier, the References/HotelKey element is used.

It needs to match the value defined within:

  • Content EDF: not used

  • Allotment EDF: BasicData/@FileKey

Source﻿

If multiple suppliers deliver data for the same hotel, the Source can be used by human readers to differentiate the EDF files.

The @Source attribute is technically processed and used to

  • identify hotel suppliers

  • identify the correct CRS routing in the booking process for dynamic packages

  • add a calculation rule (in the Calculation EDF) for a specific hotel supplier

The @Source attribute is mapped to the following positions in the Hub / B-Hub requests:

  • Hub: /HotelOfferResponse/Hotel/Offers/Offer[1]/@Provider

  • B-Hub: /CheckRequest/Offers/Offer/HotelOnly/Hotels/Hotel/Provider/@Code

It needs to match the value defined within:

  • Content EDF: not used

  • Allotment EDF: BasicData/@Source

  • Calculation EDF: HotelRestriction/Sources

TravelType / ProgramType﻿

Used for specifying a travel or program type for the given hotel contract. To sell a product with multiple travel or program types, multiple EDF files are required. The @TravelType|ProgramType attributes are used as one of the Hotel identifiers.

In packages (not dynamic), the values of TravelType and/or ProgramType in the flight EDF and the hotel EDF must match. It is used to synchronize the flights together with the hotels.

The attributes are mapped to the following positions in the Hub / B-Hub requests:

  • Hub: /HotelOfferResponse/Hotel/Offers/Offer[1]/@TravelType|ProgramType

  • B-Hub: /CheckRequest/Offers/Offer/HotelOnly/TravelType|ProgramType

It needs to match the value defined within:

  • Content EDF: not used

  • Allotment EDF: BasicData/@TravelType|ProgramType

ContractKey﻿

Used only for the Panel to identify contracts of the same hotel, see Hotel identifiers, under the same ContractKey /"contract name" provided that the Panel option is active, see "Merge Contracts".

BasicData elements﻿

The <BasicData> element may itself contain a number of elements as well. This section describes some important elements within <BasicData>.

Name﻿

Required by the XSD

This element specifies the name of the hotel. Note that the Name element is only used for reference, but is not processed.

The element is mapped to the following positions in the Hub / B-Hub requests:

  • Hub: /HotelOfferResponse/Hotel/Offers/Offer[1]/Name

  • B-Hub: /CheckRequest/Offers/Offer/HotelOnly/Hotels/Hotel/Description/Name

It needs to match the value defined within:

  • Content EDF: BasicData/Name (required in Content Player)

  • Allotment EDF: not used

References﻿

This element is used to reference additional identifiers for the hotel. May include a <GiataCode> and/or a <HotelKey>. While not required, the definition of a GIATA code is recommended.

GiataCode﻿

The References/GiataCode element is mapped to the following positions in the Hub / B-Hub requests:

  • Hub: /HotelOfferResponse/Hotel/References/GiataCode

  • B-Hub: /CheckRequest/Offers/Offer/HotelOnly/Hotels/Hotel/HotelCodes/HotelCode[1]

It needs to match the value defined within:

  • Content EDF: BasicData/References/ID including ID/@Type="Giata" (required in Content Player, only if the element BasicData/References is specified)

  • Allotment EDF: not used

HotelKey﻿

The References/HotelKey element is used as one of the Hotel identifiers. HotelKey is not part of the file name, refer to the FileKey attribute to differentiate file names.

The HotelKey element is mapped to the following positions in the Hub / B-Hub requests:

  • Hub: /HotelOfferResponse/Hotel/Offers/Offer[1]/@HotelKey

  • B-Hub: /CheckRequest/Offers/Offer/HotelOnly/Hotels/Hotel/BookingCode/@Key

Address﻿

The <Address> element contains the address information of the hotel. Several child elements can be used to specify the physical address, phone / fax number, email, and website. The address in the hotel EDF is only used for reference, but won't be populated to other components. But it is possible to calculate based on the Address/Country|City, e.g. city charges.

The location is used according to content EDF:

  • Content EDF: BasicData/GeoInfos/GeoCode/@Longitude and BasicData/GeoInfos/GeoCode/@Latitude (both required in Content Player)

  • Allotment EDF: not used

ArrivalAirports﻿

This element is used to define possible arrival airports to be assigned to the hotel. A maximum of 4 <Airport> elements may be contained; it is recommended to assign as many arrival airports as possible. If more than the maximum number are given, only the four first in alphabetical order will be processed by the Player. Note that arrival airports must be defined if the hotel is to be sold as part of a package!

The element is mapped to the following positions in the Hub / B-Hub requests:

  • Hub: /HotelOfferResponse/Hotel/Offers/Offer[1]/@NearestAirportDLC

  • B-Hub: /CheckRequest/Offers/Offer/HotelOnly/Hotels/Hotel/Destination

It needs to match the value defined within:

  • Content EDF: BasicData/Airports/Airport/@IataCode

  • Allotment EDF: BasicData/@IataCode

GeoInfos﻿

<GeoInfos> refers to the physical location of the hotel. This element may include a <Location> (country/region/city name) and/or a <GeoCode> (latitude and longitude). While it is not technically necessary to specify the location in the Hotel EDF, as the search uses the latitude and longitude information delivered by the Content Player, it is recommended to add this element anyway.

For the mapped elements, See Address.

HotelChain﻿

This element can be used to specify the hotel chain the product belongs to. To do so, an attribute for a supplier specific abbreviation (@Code) and/or a full name (@Name) can be used.

The element is mapped to the following positions in the Hub:

  • Hub: /HotelOfferResponse/Hotel/Offers/Offer[1]/Chain

  • B-Hub: not used

It needs to match the value defined within:

  • Content EDF: BasicData/HotelChain

  • Allotment EDF: not used

DRVGlobalTypes﻿

The <DRVGlobalTypes> element appears in various places within the Hotel EDF. Within <BasicData>, it is used to assign DRV GlobalTypes on the hotel level, e.g. hotel attributes or ratings.

The element is mapped to the following positions in the Hub / B-Hub requests:

    • Hub: /PackageOfferResponse/Hotel/References/DrvCode

    • B-Hub: /CheckRequest/Offers/Offer/Package/Hotels/Hotel/HotelCodes/HotelCode[1] including HotelCode/@Type=Drv

It needs to match the value defined within:

  • Content EDF: /DescriptiveData/GlobalTypes

  • Allotment EDF: not used

SellingData attributes﻿

The <SellingData> element contains information used for offer and price calculation. This includes definitions of seasons, rooms, boards, base charges etc. Important attributes of the <SellingData> element include:

Currency﻿

The @Currency attribute specifies the default currency to be used for the hotel. The currency must be defined as a 3-digit code according to the ISO-4217 standard.

The attribute is mapped to the following positions in the Hub / B-Hub requests:

  • Hub: /BaseDataRequest/@Currency

  • B-Hub: /CheckRequest/Amounts/TotalAmount/@Currency

It needs to match the code defined within:

  • Content EDF: not used

  • Allotment EDF: not used

FlightPriceTable﻿

The @FlightPriceTable is used for hotels that are sold as part of a package. With this attribute, price calculation is controlled by the hotel part of the package .

Working with price tables is another way of calculating packages (instead of working with BaseCharges/GuestCharges). When using FlightPriceTables they must be set equally for the inbound and outbound. Furthermore, it is recommended to set a default FlightPriceTable.

GrossRate﻿

@GrossRate is a boolean attribute that defines whether the given prices are gross rates (true) or net rates (false). Note that this attribute is used for reference and is not processed by the Player. Also consider that "gross" in the Peakwork-context means including taxes/fees, whereas in the travel industry it may mean including margins.

NegativeCalculation﻿

The @NegativeCalculation attribute uses a boolean value to specify whether negative values are allowed to be used for specific travellers within the calculation. Note that e.g. negative values for single charges are not forbidden regardless of the @NegativeCalculation attribute; only the calculation total for a traveller is taken into account.

ChildrenAgeOrder﻿

This attribute defines if discounts are applied to children in ascending (default) or descending order of age. The order is relevant in case of multiple defined age groups that have different rules set in regards to discounts.

CompatibleExtrasMode﻿

If this attribute is set (the only possible value is CompatibleExtrasMode="Flexible"), the best price logic is activated for the given EDF file. With the best-price logic in place, if there are multiple non-compatible extras that could be applied, the extra with the biggest reduction is used.

NightDiscountOrder﻿

The @NightDiscountOrder attribute defines the appliance order of extras. By default (NightDiscountOrder="NightsDescending"), extras that offer free nights are applied first (in order of how many free nights are offered). Alternatively (NightDiscountOrder="SortIndex"), extras can be applied in order of a freely assigned sorting index.

RecommendedSellingPrice﻿

If this boolean attribute is set to true (default is false), selling prices in the EDF file are marked as recommended sales prices (RSP). RPSs represent a recommended maximum selling price for the hotel. Calculated prices will not be allowed to exceed the defined RSPs.

The attribute is mapped to the following positions in the Hub / B-Hub requests:

  • Hub: HotelProductRequest/MaxPrice

  • B-Hub: `/CheckRequest/Amounts/TotalAmount/

It needs to match the code defined within:

  • Content EDF: not used

  • Allotment EDF: not used

SellingData elements﻿

Important elements within <SellingData> include:

Rooms﻿

(required by the XSD)

This element contains information on room availability and conditions. Details such as charges, occupancies, boards and restrictions are defined within each <Room> sub-element.

For more detailed information on rooms in the EDF, see Structure of the Rooms element in the Hotel EDF

Extras﻿

The Extras element can appear in various places within the hotel EDF. As a child of <SellingData>, this element defines product-specific extras on the hotel level.

For more detailed information on extras in the EDF, see TBA.

Restrictions﻿

Various types of restrictions can be defined to apply special conditions in regards to specific seasons, guests, etc. The Restrictions element can appear in various places within the hotel EDF.

For more detailed information on restrictions in the EDF, see TBA.

SeasonDefinitions﻿

This element is used to define time frames for each travel season. Different prices and conditions can be applied to different seasons. Season definitions are primarily used for hotels sold as part of a package. If there are no defined seasons for your hotel, it is recommended to set the season to the first and last dates for which a price is delivered within the contract.

Distribution﻿

This element contains a number of <Channel> child elements that define different distribution channels.

Exchanges﻿

The <Exchanges> element is used to define exchange rates for various currencies. It is recommended to define the most common exchange rates for a contract's given currency, especially if a less common currency is defined within the @Currency attribute.

Rounding﻿

This element can be used to define rules on how to process decimal numbers in the calculation. By default, prices are not rounded and only integers are used.

DRVGlobalTypes﻿

The <DRVGlobalTypes> element appears in various places within the Hotel EDF. Within <SellingData>, it is used to assign DRV GlobalTypes© on the hotel contract level.

Room attributes defined in <SellingData>/<DRVGlobalTypes> will be inherited to all contained rooms. Therefore, only define GlobalTypes here that are valid for all offers and rooms within the given contract. For example, GT05-AICO would be applicable on this level if all your rooms are equipped with air conditioning. On the other hand, GT13-SEVI should not be used here if not all the rooms have sea view.

FullPayerDoesNotAffectBoardCharges﻿

Since Box 1.80.

The <FullPayerDoesNotAffectBoardCharges> element allows to change the default BoardCharge. Especially, when children are counted as full payers (counted to BaseCharges/@MinChargedPersons ,resp. Occupancy/@MinChargedPersons), they can be then charged different BoardCharges than the default.

Consider to specify a BoardCharge for children/infants additionally to the default BoardCharge, e.g. <BoardCharge Amount="10.00" Board="AI" MinAge="2" MaxAge="5" MinCount="2" MaxCount="2" PersonType="C"/>

Consider that if there are multiple EDFs for the same hotel but different contracts or seasons, the FullPayerDoesNotAffectBoardCharges element must be defined in the same way across all contracts/seasons.

Note that this element does not effect GuestCharges and Extras.

Example:

Request for 2 adults and 1 child. The following occupancy is specified for the offer:

<Occupancy Max = "6" MaxAdult = "4" MaxChild = "2" Min = "1" MinAdult = "1" MinChargedPersons = "4" MinChild = "0">
	<Infants ApplyToOccupancy = "Max" MaxCount = "0"/>
	<Children MaxAge = "11" MinAge = "2"/>

The child will be charged as a full payer. In order to not charge the child with a BoardCharge for adults, you must specify SellingData/FullPayerDoesNotAffectBoardCharges as follows:

<SellingData ..>
	<FullPayerDoesNotAffectBoardCharges>
		<PersonType>C</PersonType>
	</FullPayerDoesNotAffectBoardCharges>
</SellingData>
