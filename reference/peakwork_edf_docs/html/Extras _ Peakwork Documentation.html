Extras﻿

Last modified: 25 February 2026

Extra elements can be used for various purposes, for example to apply discount or extra charges to the price or to add global types to rooms. Extras are also called "supplements" and "offers".

Examples for extras

  • charges and reductions that are related to data types (flight, hotel etc.)

  • global incentives or additional services

  • jubilee incentives

  • special offers

  • visa costs for specific destinations

  • early bird discounts

  • long stay incentives

  • free nights, stay-pay (e.g. 7 nights for the price of 6)

  • gala dinners

  • transfers

  • handling fees

Extras in hotel EDF and global extra EDF

The Extras element in the hotel EDF is used the same as in the Hotel global extra EDF. Extras in the hotel EDF are valid for the individual hotel whereas global extras are valid for all hotels (example: a 10% discount for all hotels for a certain time period). Note that transfers are handled differently. The Player merges extras from both global extra EDF and hotel EDF.

Usage

Extras may or may not be valid in the same time range (which can be controlled by restrictions). If several extras are defined for the same time range and they mustn't conflict with each other, you can use the SortIndex attribute in order to check their compatibility in a fixed order. Additionally, some extras are compatible with one another whilst others are not. To control the validity and compatibility of extras, the attributes CombiGroupId, SortIndex and the CompatibleExtras element are used.

Extras in the hotel EDF may be referenced at several levels depending if the Extras should apply to the whole product (at hotel level) or just to specific offers (at room level):

  • HotelRoot/SellingData/Extras

  • HotelRoot/SellingData/Rooms/Room/Extras/

  • HotelRoot/SellingData/Rooms/Room/ChargeBlocks/ChargeBlock/Extras (dependent on ChargeBlock/@Type: "Basic", " Override ", "Extend")

Elements and attributes of Extra﻿

Attributes:

  • GlobalType: specifies the type of extra. The values for the @GlobalType attribute are Peakwork-defined, (AT, EX, GU, HF, IN, PF, RC, RF, SK, TR, XX - see the hotel EDF schema; not to be confused with the DRVGlobalTypes).

  • ApplianceCode: specifies the code of the Extra element. This code is tour operator specific and is user-definable.

    • Consider that the value here must the same as in Appliance/@Type="Extra".

  • Type: specifies the type of the extra. This text is a tour operator specific free-text.

  • BookingCode: specifies the booking code for extra services

  • FlightReferenceCode: refers to an extra that is defined in the flight.

  • OffersAllowed: influences with which BaseCharges elements the extra can be combined.

  • Mandatory: specifies whether the price of this extra is added to the room price and whether the price of this extra is separately returned in the Player response.

  • CombiGroupId: is used to specify which group an extra belongs to. These groups can be used to combine extras. The ID can be used to reference one or more Extra elements in the CompatibleWith element (see CompatibleExtras (parent) element) This way the compatibility of extras of different groups can be controlled. The value of CombiGroupId must be an integer and the default is 0.

  • SortIndex: influences the order in which order the compatibility of the extras is checked. The smaller the value of the SortIndex attribute, the higher the priority for checking. Extras without a SortIndex attribute are checked before extras with a SortIndex attribute.

    The data type of the attribute is integer.

    Example:

    SortIndex

    Priority

    highest

    0

    high

    1

    high

    2

    high

    ...

    ...

    10

    medium

    ...

    ...

    100

    medium

    1000

    low

    1001

    low

    Please note that the SortIndex attribute controls the compatibility check but not the appliance of an extra. See also Processing order of the extras.

The Extras/Extra element consists of the following child elements:

CompatibleExtras﻿

The CompatibleExtras element is a list of CompatibleWith elements. Compatibility of extras means that extras can be combined with each other.

Consider that when not using the CompatibleExtras element, by default Extra elements will be combined with each other without any restriction.

The CompatibleWith element specifies the compatibility of the Extra element with other Extra elements. Each CompatibleWith element refers to one other Extra element. If the current Extra element has to be compatible with more than one other Extra element, one has to define more than one CompatibleWith element.

Besides its child element CompatibleWith, the CompatibleExtras element has the attributes @Invert and @ApplyTo.

For a detailed description of the CompatibleExtras element, see the section CompatibleExtras element and CompatibleWith element in the "Global Extras" chapter.

Descriptions﻿

The Descriptions element is a list of Description elements.

Note that the Extra/Description element is not processed by the Hub request and not displayed to the end customer.

The Description element includes the @Visible attribute. However, this attribute is deprecated as the Description element is not displayed to the end customer in any case.

Reductions and Charges﻿

For additional charges or price reductions, the elements Charge and Reduction can have the Appliances element with any number of Appliance sub elements to specify on what to apply the calculation. The attributes Type and Code specify to which price component (base charge, board charge etc.) or to which extra the reductions or charges are applied.

The Reductions/Reduction and Charges/Charge elements have the same elements and attributes. Note that the global extra EDF has a different structure than the hotel EDF regarding Charge and Reduction elements.

Elements:

  • Appliances, see Appliance types

  • Rounding

Attributes:

  • Amount

  • Percent

    • Note: you cannot use Percent, when BaseCharges/@CalculationMode="O" for object, see BaseCharges is used and/or the Reduction|Charge/@Calculation="P"` for person is used.

  • Mode

  • Nights

  • Calculation

  • AddToBaseCharge

  • Duration

  • BaseBoard (only for Reductions/Reduction)

  • BoardId (only for Reductions/Reduction)

  • GuestId (only for Reductions/Reduction)

  • DiscountedNights (only for Reductions/Reduction)

  • HotelPriceTable (only for Reductions/Reduction)

  • SeasonLabel (only for Reductions/Reduction)

Distribution﻿

The Distribution element is a list of Channel elements.

If an element has no Distribution element, this element is valid for all distribution channels.

INFX﻿

The INFX element defines additional information, which is written into the offer line during the INFX generation.

The INFX element is only relevant if you want to generate INFX data from EDF and the predefined INFX formats aren't sufficient.

DRVGlobalTypes﻿

You may set a reference to DRVGlobalTypes here, which the extra applies to. Mostly this is done for "GT06 Boards", "GT07 Incentives" or "GT08 Additional Services".

Note that the Extra/@GlobalType attribute is a different list of Peakwork-defined values, see Elements and attributes of Extra.

Restrictions﻿

Restrictions within extras are handled the same as on the other levels, see the Restrictions section.

Exception: Consider that only one Restriction element may occur (maxOccurs="1" for HotelRoot/SellingData/Rooms/Room/Extras/Restrictions/Restriction) whereas on other levels multiple Restriction elements are allowed (see again Restrictions).

Note that restrictions here only refer to an extra, not to a booking restriction like a minimum and maximum stays for the complete travel. If a restriction of an extra is not met, the extra won't be applied, but the booking of this stay may still be possible.

The following XML snippet shows the extra of "7=6" with the prerequisites of a certain travel period together with travel duration:

<Extra Type="7=6">
    <Restrictions>
        <Restriction>
            <DateRestrictions>
                <DateRestriction ApplyTo="Arrival" Start="2021-09-25" End="2021-10-02"/>
            </DateRestrictions>
        <StayRestrictions>
            <StayRestriction Min="P7D" Max="P13D" ApplyTo="Complete"/>
        </StayRestrictions>
        </Restriction>
    </Restrictions>
    <Reductions>
        <Reduction Percent="100.00" Mode="LastStay" DiscountedNights="1.0"/>
    </Reductions>
</Extra>

It means:

"If you arrive between 25 September 2021 and 02 October 2021(1.) AND(2.) you booked between 7 and 13 days(3.), then the last night(4.) is free(5.)."

  1. The DateRestriction element defines the restriction of the time range in which the extra applies.

  2. The elements DateRestrictions and StayRestrictions are combined by a logical AND (see Restrictions).

  3. ApplyTo="Complete" within the StayRestriction refers only to duration of the stay (7-13 days); at least one day of this duration must be within the date range of the DateRestriction.

  4. Mode= "LastStay" refers to the last night(s) of the stay which the extra applies to, having DiscountedNights="1.0" only the one night will be considered

  5. The extra is a reduction of 100% (for the last night, which is also referred to as "7=6").

This XML example will be used as a base example for the following section "Condition, Invert, Operator attributes in the Restrictions elements", to show the changes when using the "...Restrictions " elements' attributes @Invert, @Condition and @Operator differently.

For another example of an restriction, read also DateRestriction within Extra in the "Global Extras" chapter.

Condition, Invert, Operator attributes in the Restrictions elements﻿

For almost each "...Restrictions " element you have the attributes @Invert, @Conditionand @Operator with the following values:

  • @Invert: false (default value), true

  • @Condition: true (default value), false

  • @Operator: OR (default value), AND

In case of the elements DateRestrictions, StayRestrictions, WeekdayRestrictions within the Extra element, the attributes may change the relation and application of the restrictions and thereby the prerequisites of an extra.

Consider that both the HotelRestrictions and GuestRestrictions elements have neither @Condition nor @Operator attributes and the BoardRestrictions element has no @Operator attribute, whereas the GuestRestrictions` element has a special role, see Operator.

In the following, it will be described how the attributes @Invert, @Condition and @Operator can change the prerequisites of the extra described in the base example in the Restrictions section.

Invert﻿

The @Invert attribute specifies whether the condition in the "...Restrictions" element is inverted.

Using DateRestrictions Invert="true" in the example, it will reverse the date range for the extra to apply. The extra would be valid for the whole year, except the week from 25.09. to 02.10.2021:

"If you do not arrive between 25 September 2021 and 02 October 2021 AND you booked between 7 and 13 days, then the last night is free."

<Extra Type="7=6">
    <Restrictions>
        <Restriction>
            <DateRestrictions Invert="true">	<!---ADDED INVERT-ATTRIBUTE -->
                <DateRestriction ApplyTo="Arrival" Start="2021-09-25" End="2021-10-02"/>
            </DateRestrictions>
        <StayRestrictions>
            <StayRestriction Min="P7D" Max="P13D" ApplyTo="Complete"/>
        </StayRestrictions>
        </Restriction>
    </Restrictions>
    <Reductions>
        <Reduction Percent="100.00" Mode="LastStay" DiscountedNights="1.0"/>
    </Reductions>
</Extra>

Condition﻿

As described in Restrictions, several "...Restrictions" element are combined by a logical AND. This is described by @Condition="true" (default value).

@Condition="false" can change this relation to an if-then-relation. Structure of an if-then-relation: "If condition A is met, then restriction B applies." The if-part describes the condition. The then-part describes the restriction (Condition="false").

XML example:

The DateRestrictions element (implicitly) has Condition="true" and thus belongs to the if-part of the if-then-relation. The StayRestrictions element has Condition="false" and thus belongs to the then-part of the if-then-relation:

"If you arrive between 25 September 2021 and 02 October 2021, you must book between 7 and 13 days, for the extra to apply (then the last night is free)."

<Extra Type="7=6">
    <Restrictions>
        <Restriction>
            <DateRestrictions>
                <DateRestriction ApplyTo="Arrival" Start="2021-09-25" End="2021-10-02"/>
            </DateRestrictions>
        <StayRestrictions Condition="false">	<!---ADDED CONDITION-ATTRIBUTE -->
            <StayRestriction Min="P7D" Max="P13D" ApplyTo="Complete"/>
        </StayRestrictions>
        </Restriction>
    </Restrictions>
    <Reductions>
        <Reduction Percent="100.00" Mode="LastStay" DiscountedNights="1.0"/>
    </Reductions>
</Extra>

As this result has more or less the same meaning as the base example, we add another example that shows the behavior of Condition=false:

Example 2:

Meaning: "If you arrive between 25 September 2021 and 02 October 2021, you must book either 7 or 14 days, for the extra to apply (then the last night is free)."

<Extra Type="7=6">
	<Restrictions>
		<Restriction>
			<DateRestrictions>
                <DateRestriction ApplyTo="Arrival" Start="2021-09-25" End="2021-10-02"/>
            </DateRestrictions>
			<StayRestrictions Condition="false">		<!---ADDED CONDITION-ATTRIBUTE -->
				<StayRestriction Min="P7D" Max="P7D" ApplyTo="Complete"/>
				<StayRestriction Min="P14D" Max="P14D" ApplyTo="Complete"/>
			</StayRestrictions>
		</Restriction>
	</Restrictions>
	<Reductions>
        <Reduction Percent="100.00" Mode="LastStay" DiscountedNights="1.0"/>
    </Reductions>
</Extra>

Operator﻿

The @Operator attribute specifies how subordinate restrictions are related to each other. By default, "...Restriction" elements have an either/or-relation, as seen for the two StayRestriction in "Example 2" in the Condition section.

The @Operator attribute is only useful for the WeekdayRestrictions element. Example:

Meaning: "If you arrive between 25 September 2021 and 02 October 2021, you must book either 7 or 14 days AND you must arrive on Saturday and depart on Sunday, for the extra to apply (then the last night is free)."

<Extra Type="7=6">
	<Restrictions>
		<Restriction>
			<DateRestrictions>
                <DateRestriction ApplyTo="Arrival" Start="2021-09-25" End="2021-10-02"/>
            </DateRestrictions>
			<WeekdayRestrictions Condition="false" Operator="AND"> 	<!---ADDED OPERATOR-ATTRIBUTE -->
				<WeekdayRestriction ApplyTo="Arrival" Mask="NNNNNYN"/>
				<WeekdayRestriction ApplyTo="Departure" Mask="NNNNNY"/>
			</StayRestrictions>
			<StayRestrictions Condition="false">
				<StayRestriction Min="P7D" Max="P7D" ApplyTo="Complete"/>
				<StayRestriction Min="P14D" Max="P14D" ApplyTo="Complete"/>
			</StayRestrictions>
		</Restriction>
	</Restrictions>
	<Reductions>
        <Reduction Percent="100.00" Mode="LastStay" DiscountedNights="1.0"/>
    </Reductions>
</Extra>

GuestRestrictions element

Note that the GuestRestrictions element has no @Operator attribute, nevertheless GuestRestriction elements are automatically combined by AND. Consider that in GuestRestriction/@PersonType the person type infant ("I") is not supported when used within an Extra. Example:

Meaning: "If you arrive between 25 September 2021 and 02 October 2021, you must book either 7 or 14 days AND a max. of 2 adults and at least one child must travel, for the extra to apply (then the last night is free)."

<Extra Type="7=6">
	<Restrictions>
		<Restriction>
			<DateRestrictions>
                <DateRestriction ApplyTo="Arrival" Start="2021-09-25" End="2021-10-02"/>
            </DateRestrictions>
			<GuestRestrictions Condition="false"> 		<!--NO OPERATOR-ATTRIBUTE NEEDED-->
				<GuestRestriction MinPerson="2" MaxPerson="2" PersonType="A"/>
				<GuestRestriction MinPerson="1" PersonType="C"/>
			</StayRestrictions>
			<StayRestrictions Condition="false">
				<StayRestriction Min="P7D" Max="P7D" ApplyTo="Complete"/>
				<StayRestriction Min="P14D" Max="P14D" ApplyTo="Complete"/>
			</StayRestrictions>
		</Restriction>
	</Restrictions>
	<Reductions>
        <Reduction Percent="100.00" Mode="LastStay" DiscountedNights="1.0"/>
    </Reductions>
</Extra>

Extras and duration﻿

This section describes the relation of BaseCharges/BaseCharge/@Duration attribute and extras.

In the case that Duration="P1D" is specified in the according BaseCharge element, the behavior of Extras is quite intuitive.

But for longer durations, the price influenced by an extra may be in turn influenced by the requested number of days. That is the case when the requested length of stay is shorter than the Duration attribute given in the according BaseCharge. In such cases the price for the excess days has to be subtracted. The resulting price will be the base price for the specific length of stay.

The following two examples should explain the behavior more explicitly. The first one is straightforward, the second one covers the more peculiar case.

Example 1:

If we have an extra with the following specifications:

How to specify that a minimum number of qualifying nights must lie within the DateRestriction for the Extra to apply?﻿

For this use case, use the DateRestrictions/DateRestriction element together with the @ApplyTo="Stay" attribute/value.

XML example:

<Extra ApplianceCode="extra_x" CombiGroupId="1" SortIndex="1" >
	<Restrictions>
		<Restriction>
			<DateRestrictions Condition="true">
				<DateRestriction ApplyTo="Stay" Start="2021-03-10" End="2021-03-20"/>
			</DateRestrictions>
			<StayRestrictions Condition="false">
				<StayRestriction ApplyTo="Stay" Min="P4D"/>
			</StayRestrictions>
		</Restriction>
	</Restrictions>
	<CompatibleExtras>
		<CompatibleWith GroupId="1"/>
	</CompatibleExtras>
	<Descriptions>
		<Description>Minimum Stay Discount</Description>
	</Descriptions>
	<Reductions>
		<Reduction Amount="50.00" Calculation="ON" />
	</Reductions>
</Extra>

The extra "extra_x" (50€ reduction) is valid in the travel date range 10th March 2021 – 20th March 2021. This extra is only valid if at least 4 days of the stay are within this date range.

If a stay lies between March 18th and March 25th, the system will not apply the extra, because only 3 of the 7 stay nights fall within the qualifying period.
If a stay lies between March 15th and March 22th, the system will apply the extra since 6 of the 7 stay nighs fall within the qualifying period.
