Meta-booking OTA/HTNG hotel booking API﻿

Last modified: 25 February 2026

This documentation defines the XML API based on the OTA/HTNG standard that Peakwork partners can use to enable direct bookings from Meta Ads properties.

The OTA specifications define messages for many travel services including hotel availability and reservations. Based on these generic messages, the HTNG technical specifications provide concrete guidelines which messages and fields to use in specific scenarios.

The relevant HTNG specification for booking hotel rooms is the Distribution Interface Specification " Product Distribution ­ Seamless Shop/Book ". It uses the OTA message pairs OTA_HotelAvailRQ/RS and OTA_HotelResRQ/RS.

Most organizations supporting the OTA interface follow the HTNG specification. Although the HTNG recommendations clarify the use of the OTA messages, there is still room for variations. This documentation defines which elements and attributes are used by the Meta-booking OTA/HTNG API when requesting availability and booking reservations.

References﻿

  • OTA XML schema. Peakwork currently supports version 2008A.

  • HTNG Product Distribution Seamless Shop/Book 2014B Specification.

The following section describes general guidelines for all message types.

Message format﻿

The Meta-booking OTA/HTNG API uses the standard OTA XML message format with the standard namespace "http://www.opentravel.org/OTA/2003/05".

With few exceptions, the elements and attributes used by the Meta-booking OTA/HTNG API are available in all versions following 2005B. As stated above, we are using version 2008A for the client software.

As specified by HTNG, the OTA XML messages are exchanged using SOAP (document/literal style) over HTTPS. The requests will contain the HTNG authentication headers with the username and password for the Metasearch client as agreed on with the partner. The partner system must validate these headers and reject the request if the provided credentials are not valid.

Example: Authentication

<?xml version="1.0" encoding="UTF­8"?>

<SOAP­ENV:Envelope xmlns:SOAP­ENV="http://schemas.xmlsoap.org/soap/envelope/"> <SOAP­ENV:Header>
	<HTNGHeader xmlns="http://htng.org/1.1/Header/"> <From>
			<Credential>
				<userName>Username of the metasearcher</userName>
				<password>secret</password>
			</Credential>
		</From>
	</HTNGHeader>
</SOAP­ENV:Header>
<SOAP­ENV:Body>
	<OTA_HotelAvailRQ xmlns="http://www.opentravel.org/OTA/2003/05" EchoToken="12345"
PrimaryLangID="en">

...
	</OTA_HotelAvailRQ>
</SOAP­ENV:Body>

</SOAP­ENV:Envelope>

General Formatting﻿

Dates and times﻿

All dates use the standard XML schemadate format which is consistent with ISO 8601 without timezone, e.g., "2019­10­15". The implicit time zone is the time zone of the hotel. Date ranges do not include the end date. For example, the element

<StayDateRange Start="2019­10­15" End="2019­10­17"/>

specifies a stay for two nights from the arrival (check­in) date "2019­10­15" to the departure (check­out) date "2019­10­17".

Similarly, date­time values use the standard XML schema dateTime format, e.g., "2019­10­15T16:00:00".

Monetary amounts﻿

Monetary amounts (such as RoomRate/Rates/Rate/Base) must contain

  • CurrencyCode (three letter ISO 4217 code)

  • Amount as decimal string

The DecimalPlaces attribute should not be used. The number of decimal places is implicitly defined by the decimal string representation of the amounts. Trailing zeros should not be omitted, that is, the representation of $150.50 is "150.50" and not "150.5".

Common elements and attributes﻿

Request identifier (EchoToken)﻿

Each request contains a unique identifier (UUID) in the EchoToken attribute that has to be echoed in the associated response.

User language﻿

The user's preferred language is contained in the PrimaryLangID attribute of every request.

Descriptions (e.g., rate plan, room type) should be returned in the specified language.

If a Text element in a response does not have a Language attribute, the text is assumed to be in the language specified in the PrimaryLangID attribute of the request.

POS element﻿

The POS element is the same for all requests and identifies the requestor (for internet broker Type="13" is used).

<POS>
<Source>
	<RequestorID Type=”13” ID=”ID of the metasearcher”/>
	<BookingChannel Primary=”1” Type=”7”>
		<CompanyName>Name of the company</CompanyName>
	</BookingChannel>
</Source>

</POS>

Error handling﻿

The error handling distinguishes the following kinds of errors:

  • communication errors (unreachable server, broken connection, timeout)

  • syntax, validation errors (malformed request, missing data)

  • function/business errors (availability, rate mismatches)

  • system failures (internal server errors)

Communication errors﻿

Communication errors (server unreachable, timeout) should be returned using the appropriate HTTP status codes. In the absence of communication errors, the response body should be a well formed SOAP envelope. The body of the SOAP envelope must contain either a fault or the OTA response message (which may contain a success result or error elements).

Syntax and validation errors﻿

Syntax and validation errors (for example, a malformed XML or SOAP message) should be returned as a SOAP fault. If the SOAP body does not contain a fault, it must contain the OTA response message corresponding to the request (for example, OTA_HotelAvailRS response for OTA_HotelAvailRQ request).

Business errors﻿

Business errors should be returned in the Errors element of the OTA response message.

As specified by HTNG, if the response contains the Errors element, this element will be the only child of the root element. Otherwise, the root element will contain the Success child element and the actual response data (for example, the RoomStays element in the OTA_HotelAvailRS).

System failures﻿

System errors such as internal server errors can be reported either as HTTP errors (e.g., 500, Internal Server Error) or SOAP faults.

Request sequence﻿

The Meta-booking flow uses three requests, two availability requests and one reservation request:

  • initial availability request (OTA_HotelAvailRQ)

  • availability check before book request (OTA_HotelAvailRQ)

  • book request (OTA_HotelResRQ)

The initial availability request asks for the availability data for the hotel stay selected by the user. The provided information includes the hotel, stay period (arrival, departure), guests counts and optionally an identification of the selected rate (see below).

The partner returns one or more room rates satisfying the request, and the Meta-booking logic selects the rate that matches the request or offers the user to choose from the returned results. The rate or rates are shown to the user in the Meta-booking user interface. Due to differences between the pricing feed and the rates obtained through the OTA/HTNG API, the rates may differ slightly from the rate shown in the Metasearch Ads (which is made clear in the UI).

Once the user has confirmed the selection and entered the additional data required for the booking, the Meta-booking flow first issues a second availability request to ensure that the rate has not changed in the meantime. This request contains the room type and rate plan identification that was returned by the partner in the initial availability response (OTA_HotelAvailRS). If the new availability response matches the expected one (that was selected by the user), the Metasearch engine sends the reservation request (OTA_HotelResRQ) with this rate and the additional customer and payment information.

Availability﻿

Availability request﻿

The Metasearch engine will send an OTA_HotelAvailRQ with the following elements:

  • Single hotel itinerary (AvailRequestSegment element)

  • Single hotel search criterion (HotelSearchCriteria/Criterion) with

    • hotel reference with partner hotel ID as HotelCodeattribute

    • stay period as StayDateRangeelement

    • single RoomStayCandidate element with quantity and guest counts

  • The GuestCount elements have the AgeQualifyingCode and Count attributes set. At this point, the only AgeQualifyingCode values used are "10" (Adult) and "8" (Child). In case of children, the Age attribute will be set as well.

  • The RoomStayCandidate element may contain a RoomTypeCode attribute.

  • The Criterion element may contain a single RatePlanCandidateelement (RatePlanCandidates/RatePlanCandidate) containing a RatePlanCode attribute.

Example: Availability request

Initial request without room type or rate plan code:

<OTA_HotelAvailRQ xmlns="http://www.opentravel.org/OTA/2003/05" EchoToken=”12345”>
	<POS>
		<Source>
			<RequestorID Type=”” ID=”ID of the metasearcher”/>
			<BookingChannel Primary=”1” Type=”7”>
				<CompanyName>Name of the company</CompanyName>
			</BookingChannel>
		</Source>
	</POS>
	<AvailRequestSegments>
		<AvailRequestSegment>
			<HotelSearchCriteria>
				<Criterion>
					<HotelRef HotelCode=”1000”/>
					<StayDateRange Start=”2019­04­15” End=”2019­04­17”/> <RoomStayCandidates>
							<RoomStayCandidate Quantity=”1”>
							<GuestCounts>
								<GuestCount AgeQualifyingCode=”10” Count=”2”/> </GuestCounts>
							</RoomStayCandidate>
					</RoomStayCandidates>
				</Criterion>
			</HotelSearchCriteria>
		</AvailRequestSegment>
	</AvailRequestSegments>
</OTA_HotelAvailRQ>

Subsequent request with room type and rate plan code:

<OTA_HotelAvailRQ xmlns="http://www.opentravel.org/OTA/2003/05" EchoToken=”12345”>
	<POS>
		<Source>
			<RequestorID Type=”13” ID=”ID of the metasearcher”/>
			<BookingChannel Primary=”1” Type=”7”>
				<CompanyName>Name of the company</CompanyName>
			</BookingChannel>
		</Source>
	</POS>
	<AvailRequestSegments>
		<AvailRequestSegment>
			<HotelSearchCriteria>
				<Criterion>
					<HotelRef HotelCode=”1000”/>
					<StayDateRange Start=”2019­04­15” End=”2019­04­17”/> <RoomStayCandidates>
							<RoomStayCandidate Quantity=”1” RoomTypeCode=”DBL”> <GuestCounts>
									<GuestCount AgeQualifyingCode=”10” Count=”2”/> </GuestCounts>
						</RoomStayCandidate>
					</RoomStayCandidates>
					<RatePlanCandidates>
						<RatePlanCandidate RatePlanCode=”STD”/>
					</RatePlanCandidates>
				</Criterion>
			</HotelSearchCriteria>
		</AvailRequestSegment>
	</AvailRequestSegments>
</OTA_HotelAvailRQ>

Availability response﻿

If the request could be processed successfully, the OTA_HotelAvailRS response returned by the partner should contain the following elements:

  • empty Success element

  • single RoomStay element with

    • TimeSpan containing the stay period as specified in the request.

    • BasicPropertyInfo containing the hotel reference (HotelCode and ChainCode if necessary) as specified in the request.

    • GuestCounts as provided in request.

    • RoomTypes with one or more RoomType elements identified by the RoomTypeCode attribute.

    • RatePlans with one or more RatePlan elements identified by the RatePlanCode attribute.

    • RoomRates with one or more RoomRate elements.

  • each RoomType element must have

    • RoomTypeCode attribute: identifies the room rate within the RoomStay.

    • a RoomDescription element with

      • Name attribute: short descriptive name of the room type.

      • One or more Text elements describing the room type (sentence or short paragraph).

      • One or more Image elements, each containing a URL for an image of the room.

  • each RatePlan element must have

    • RatePlanCode attribute: identifies the rate plan within the RoomStay.

    • a RatePlanDescription element with

      • Name attribute: short descriptive name of the rate plan.

      • One or more Text elements describing the rate plan (sentence or short paragraph).

    • the RatePlan elements should include the rate plan's terms using the OTA elements

      • Guarantee

      • CancelPenalties/CancelPenalty

  • each RoomRate element represents one complete quote and must

    • reference a RoomType and a RatePlan element contained in the RoomStay element using the RoomTypeCode and RatePlanCodeattributes

    • cover the entire stay period and should therefore omit the effective date attributes

    • contain the Total element providing the total rate for the whole stay

    • contain one or more rates

  • the RoomRate/Total element must contain the CurrencyCode attribute and at least one of the attributesAmountBeforeTax and AmountAfterTax depending on the local jurisdiction. In the US, for example, both attributes, AmountBeforeTax and AmountAfterTax must be provided.

  • each Rate element

    • must contain a Base element with

      • AmountBeforeTax attribute (depending on jurisdiction)

      • AmountAfterTax attribute (depending on jurisdiction)

      • CurrencyCode attribute

      • Tax element with Amount and CurrencyCode attributes

    • should not contain any policy elements (they should be provided in the RatePlan elements instead)

  • a Rate element may specify an effective date range using the EffectiveDate and ExpireDate attributes. Following out date range convention, the ExpireDate attribute is not included in the range. The effective date range of the Rates contained in a RoomRate must form a partition of the whole stay period, that is, every night must be covered by exactly one rate.

  • all currency codes must be identical, that is, all monetary values in the availability response must use the same currency.

The Text elements of a description (OTA ParagraphType) will be concatenated and shown to the user as a single text block. The text may contain (XML­escaped) HTML markup. This markup is converted to a suitable plain text representation (formatting paragraphs and lists, for example).

Example: Availability response (Success)

<OTA_HotelAvailRS xmlns="http://www.opentravel.org/OTA/2003/05" EchoToken=”12345”>
<Success/>
<RoomStays>
	<RoomStay>
		<RoomTypes>
			<RoomType RoomTypeCode=”KING”> <RoomDescription Name=”Superior King”>
						<Text>...</Text>
				</RoomDescription>
			</RoomType>
			<RoomType RoomTypeCode=”SUITE”>
				<RoomDescription Name=”Excutive Suite”>
					<Text>...</Text>
				</RoomDescription>
			</RoomType>
		</RoomTypes>
		<RatePlans>
			<RatePlan RatePlanCode=”STD”>
				<RatePlanDescription Name=”Best Rate Available”>
					<Text>...</Text>

Rate plan policies﻿

The RatePlan element may contain the policy elements:

  • CancelPenalties

  • Guarantee

A rate is considered refundable if the RatePlan element contains at least one CancelPenalties/CancelPenalty element. The PenaltyDescription/Text of the first CancelPenalty is presented to the user.

Example:

<RatePlan RatePlanCode=”STD”>
<RatePlanDescription Name=”...”>
	<Text>...</Text>
</RatePlanDescription>
...
<CancelPenalties>
	<CancelPenalty>
		<PenaltyDescription>
			<Text>Cancellation without penalty up to 72hr prior to arrival.</Text>
		</PenaltyDescription>
	<CancelPenalty>
<CancelPenalties>
...
</RatePlan>

The API supports the structured CancelPenalty information as contained in the Deadline and AmountPercent child element and the NonRefundable attribute.

The Deadline may be specified as an AbsoluteDeadline (XML date­time value) or a relative deadline given in terms of theOffsetDropTime,OffsetTimeUnit, andOffsetUnitMultiplierattributes. The cancel penalty can be provided explicitly (rather than just in the rate plan description) in theAmountPercentelement as an absolute Amount andCurrencyCode, aPercent(of the total amount for the room stay), or aNmbrOfNights`.

Example:

<RatePlan RatePlanCode=”STD”>
<RatePlanDescription Name=”...”>
	<Text>...</Text>
</RatePlanDescription>
...
<CancelPenalties>
	<CancelPenalty>
		<PenaltyDescription>
			<Text>Cancel up to three days before arrival to avoid the</Text> <Text>fee of one night room and tax.</Text>
		</PenaltyDescription>
		<CancelPenalty>
			<Deadline OffsetDropTime="BeforeArrival" OffsetTimeUnit="Day" OffsetUnitMultiplier="3"/>
				<AmountPercent NmbrOfNights="1"/>
	</CancelPenalty>
	<CancelPenalty>
<CancelPenalties>
...
</RatePlan>

As defined in the OTA specification, the NonRefundable attribute of a CancelPenalty indicates that any prepayment for the reservation is non­refundable, and that the Deadline element is ignored.

A rate is considered prepaid if the RatePlan contains a Guarantee element with the GuaranteeType attribute "PrePay" or "DepositRequired", that is, if the customer has to pay some amount of the rate at the time of booking. The GuaranteeDescription/Text of the first Guarantee element is presented to the user.

Example:

<RatePlan RatePlanCode=”STD”>
<RatePlanDescription Name=”...”>
	<Text>...</Text>
</RatePlanDescription>
...
<Guarantee GuaranteeType=”PrePay”>
	<GuaranteeDescription>
		<Text>Full amount has to be paid at time of booking.</Text>
	</GuaranteeDescription>
<Guarantee>
...
</RatePlan>

Reservation﻿

Book request﻿

For the reservation an OTA_HotelResRQ request will be sent.

The reservation request contains:

  • a single Reservation (HotelReservation) with a single RoomStay element containing

    • selected hotel (BasicPropertyInfo), stay period (TimeSpan ),guest counts

    • a single RoomRate as received in the response (OTA_HotelAvailRS) to the preceding availability request

    • total amount (Total element)

    • credit card data either as guarantee (GuaranteeAccepted) or deposit (AcceptedPayment)

  • guest information (HotelReservation/ResGuests)

    • name and contact information in ProfileInfo

Hotel identification, stay period, and guest counts are identical to the preceding availability request. The RoomRate is identified by its attributes RoomTypeCode and RoomRateCode. The reservation request will include at least the Total element.

The reservation request must be rejected if the rate is no longer available or the total price provided in the reservation request does not match the price expected by the partner.

Book response﻿

The OTA_HotelResRS reservation response echoes most of the information of the reservation request and adds the status and identification of the reservation in the partner system.

As specified by HTNG, the reservation locator is returned in the HotelReservationID element in HotelReservation/ResGlobalInfo. The HotelReservationIDs element must contain a single HotelReservationID element with the reservation locator in the ResID_Value attribute. The ResID_Type can be chosen by the responding system and is not validated or interpreted by the Meta-booking OTA/HTNG engine.
